# 방탈출 예약 관리 — Spring MVC 인증과 Spring Data JPA

로그인 인증과 관리자 권한 검사를 기반으로 예약을 생성하고, JPA를 이용한 내 예약 조회와 예약 대기 신청·취소를 구현합니다.

## 1단계 — 로그인

- 이메일과 비밀번호를 확인해 JWT를 발급하고 HttpOnly 쿠키에 저장합니다.
- 토큰을 검증해 로그인한 회원을 조회하고, 로그아웃하면 쿠키를 만료시킵니다.
- 인증 실패는 401, 권한 부족은 403, 잘못된 입력은 400으로 응답합니다.
- 예상하지 못한 서버 오류는 400으로 변환하지 않고 500으로 처리합니다.

| 메서드 | 경로 | 기능 |
| --- | --- | --- |
| POST | /login | 로그인 및 토큰 발급 |
| GET | /login/check | 로그인 회원 조회 |
| POST | /logout | 로그아웃 |

## 2단계 — 로그인 리팩터링

- CookieTokenExtractor가 쿠키에서 토큰을 추출합니다.
- LoginMemberArgumentResolver가 LoginMember를 컨트롤러에 전달합니다.
- 컨트롤러는 예약 서비스에 로그인 회원 ID만 전달합니다.
- ReservationRequest는 record로 정의합니다.
- 회원 기능은 member, 인증·인가 기능은 auth 패키지로 분리합니다.

### 예약 생성

POST /reservations 요청에는 date, theme, time과 선택적인 memberId를 전달합니다.

| 요청 조건 | 예약자 |
| --- | --- |
| `memberId`가 없으면 | 로그인한 회원 |
| 관리자가 `memberId`를 지정하면 | 해당 ID의 회원 |
| 일반 회원이 다른 회원의 `memberId`를 지정하면 | 403 반환 |

동명이인을 구분하기 위해 이름 대신 회원 ID를 사용합니다. 관리자 예약 화면에서도 예약할 회원 ID를 입력합니다.

## 3단계 — 관리자 기능

AdminInterceptor는 컨트롤러 메서드의 @AdminOnly를 확인합니다.
관리자 판단은 Member.isAdmin()에서 수행하고 LoginMember가 위임합니다.

- `HandlerInterceptor`를 구현해 컨트롤러 실행 전에 관리자 권한을 검사합니다.
- Interceptor는 전체 경로에 등록하고, `@AdminOnly`가 붙은 컨트롤러 메서드에서 관리자 권한을 검사합니다.
- 토큰을 검증하고 조회한 회원의 역할이 `ADMIN`인지 확인합니다.
- 관리자 페이지와 예약 삭제, 시간·테마 생성 및 삭제 API에 `@AdminOnly`를 적용합니다.
- 인증 실패는 `401 Unauthorized`, 로그인했지만 관리자 권한이 없는 경우는 `403 Forbidden`을 반환합니다.

- GET /admin, /admin/reservation, /admin/theme, /admin/time
- GET /members
- DELETE /reservations/{id}
- POST /themes, DELETE /themes/{id}
- POST /times, DELETE /times/{id}

예약 생성은 일반 회원도 이용할 수 있습니다. 테마·시간·예약 목록 조회는 공개합니다.

| 사용자 상태 | 관리자 기능 접근 |
| --- | --- |
| 관리자 | 허용 |
| 일반 회원 | 403 반환 |
| 비로그인 | 401 반환 |
| 유효하지 않은 토큰 | 401 반환 |

## 4단계 — JPA 전환

### 구현 내용

- JDBC 의존성을 `spring-boot-starter-data-jpa`로 교체했습니다.
- `Member`, `Time`, `Theme`, `Reservation`에 엔티티 매핑을 적용했습니다.
- `Reservation`에서 회원·시간·테마를 `@ManyToOne`과 `@JoinColumn`으로 연결했습니다.
- 사용하지 않는 JDBC DAO 네 개를 제거하고 `JpaRepository`로 저장·조회·삭제를 처리합니다.
- 기본 제공 메서드로 처리할 수 없는 조회에는 쿼리 메서드를 사용합니다.
- 서비스의 조회에는 `@Transactional(readOnly = true)`, 쓰기에는 `@Transactional`을 적용했습니다.
- 목록에서 필요한 시간·테마는 `@EntityGraph`로 함께 조회합니다.

### 기존 동작 유지

시간과 테마는 `deleted` 값을 변경하는 소프트 삭제를 유지했습니다. 삭제된 항목은 선택 목록과 신규 예약에서 제외하지만, 기존 예약은 연결된 시간과 테마를 계속 조회할 수 있습니다.

예약에는 회원 참조와 예약 당시의 이름을 함께 저장합니다. 회원 ID는 예약자 식별에, 이름은 기존 예약 응답에 사용합니다.

### DB 초기화

`spring.jpa.hibernate.ddl-auto=create-drop`으로 JPA가 테이블을 생성하고, `spring.jpa.defer-datasource-initialization=true` 설정으로 이후에 `data.sql`의 초기 데이터를 입력합니다. 기존 `schema.sql`의 테이블 생성문은 제거했습니다.

H2 메모리 DB를 사용하므로 앱을 재시작하면 입력했던 데이터는 사라지고 초기 데이터로 시작합니다. 현재 설정은 학습·로컬 실행용입니다.

## 5단계 — 내 예약 목록 조회

### 요청 처리 흐름

1. `GET /reservations-mine` 요청의 토큰 쿠키를 기존 ArgumentResolver에서 검증합니다.
2. 컨트롤러가 전달받은 `LoginMember`의 ID로 조회 서비스를 호출합니다.
3. `findByMember_IdOrderByIdAsc`로 로그인한 회원의 예약만 조회합니다.
4. `MyReservationResponse`로 변환해 테마, 날짜, 시간, 상태를 반환합니다.

조회할 회원 ID를 요청 파라미터로 받지 않고 로그인 정보에서 가져오므로 다른 회원의 예약 목록을 지정해서 조회할 수 없습니다. 동명이인도 ID로 구분합니다.

| 메서드 | 경로 | 역할 |
| --- | --- | --- |
| GET | `/reservation-mine` | 내 예약 HTML 화면 |
| GET | `/reservations-mine` | 로그인한 회원의 예약·대기 JSON 목록 |

기존 예약 생성·관리 응답과 내 목록 응답의 역할이 달라 `MyReservationResponse`를 별도로 만들었습니다. 조회 기능은 `MyReservationController`와 `MyReservationService`에 분리했습니다.

## 6단계 — 예약 대기 기능

### 구현 내용과 정책

- `Waiting` 엔티티는 회원·시간·테마와 다대일 관계를 가집니다.
- 이미 예약된 날짜·테마·시간에만 대기를 신청할 수 있습니다.
- 예약자 본인은 자신의 예약에 대기할 수 없습니다.
- 동일 회원은 같은 날짜·테마·시간에 한 번만 대기할 수 있습니다.
- 대기 취소는 신청한 본인만 가능합니다.
- 내 예약 목록에 예약과 대기를 함께 반환하며, 대기에는 현재 순번을 표시합니다.
- 예약 취소 후 대기를 자동으로 예약으로 전환하는 기능은 구현 범위에 포함하지 않았습니다.

### 중복 방지

서비스의 존재 여부 검사와 DB의 유니크 제약을 함께 사용합니다.

| 테이블 | 유니크 제약 대상 | 목적 |
| --- | --- | --- |
| `reservation` | `date`, `theme_id`, `time_id` | 같은 슬롯의 중복 예약 방지 |
| `waiting` | `member_id`, `date`, `theme_id`, `time_id` | 회원별 같은 슬롯의 중복 대기 방지 |

서비스 검사 후 동시에 저장 요청이 들어오는 경우에도 DB 제약이 중복 행 저장을 막습니다. 다만 동시 요청에서 신청 순서와 응답 순번의 일관성까지 보장하는 잠금 처리는 구현하지 않았습니다.

### 대기 순번 계산

`WaitingRepository.countAhead()`의 JPQL로 같은 날짜·테마·시간에서 자신의 ID보다 작은 대기 수를 조회하고 1을 더합니다. 이 구현은 ID 순서를 대기 순서로 사용합니다.

순번은 별도 컬럼으로 저장하지 않고 조회 시 계산합니다. 앞선 대기가 삭제되면 다음 조회에서 순번이 자동으로 당겨집니다. 목록 조회는 내 대기를 먼저 가져온 뒤 각 대기의 순번을 조회하므로 대기 수만큼 추가 쿼리가 발생합니다. 현재는 학습 단계에서 흐름을 명확히 하기 위해 이 방식을 선택했습니다.

### 응답과 화면 연결

예약 행에는 `reservationId`, 대기 행에는 `waitingId`를 반환하고 해당하지 않는 ID는 `null`로 둡니다. 서로 다른 테이블에서 같은 숫자 ID가 나와도 구분할 수 있도록 했습니다.

- 예약 상태: `예약`
- 대기 상태: `1번째 예약대기`, `2번째 예약대기` 등
- 대기 신청 응답: `id`, `waitingNumber`
- 대기 취소 버튼: `waitingId`를 사용해 삭제 요청

| 메서드 | 경로 | 성공 | 주요 실패 응답 |
| --- | --- | --- | --- |
| POST | `/waitings` | 201 | 비로그인 401, 중복·예약 없는 슬롯·본인 예약 400 |
| DELETE | `/waitings/{id}` | 204 | 비로그인 401, 다른 회원의 대기 403, 없는 대기 400 |
| GET | `/reservations-mine` | 200 | 비로그인·유효하지 않은 토큰 401 |

## 실행 방법

Java 17을 사용합니다. IntelliJ의 Project SDK와 Gradle JVM도 Java 17로 맞춥니다.

Windows PowerShell:

```powershell
.\gradlew.bat bootRun
```

기본 주소는 `http://localhost:8080`입니다. 이미 같은 포트에서 앱이 실행 중이면 기존 앱을 종료하고 실행합니다.

### 초기 계정

| 회원 ID | 역할 | 이메일 | 비밀번호 |
| --- | --- | --- | --- |
| 1 | 관리자 | `admin@email.com` | `password` |
| 2 | 일반 회원 | `brown@email.com` | `password` |

초기 데이터에는 어드민의 `2024-03-01` 예약 세 건이 있습니다. 날짜·시간·테마 ID가 각각 `(2024-03-01, 1, 1)`, `(2024-03-01, 2, 2)`, `(2024-03-01, 3, 3)`인 슬롯입니다. 브라운으로 로그인하면 해당 슬롯에 대기를 신청할 수 있습니다.

## 테스트와 빌드


## 리뷰어님께

4단계에서는 직접 SQL을 실행하던 DAO를 JPA Repository로 전환하고 기존 회원 식별 방식과 소프트 삭제 동작을 유지했습니다. 5단계에서는 인증된 회원 ID로만 조회하는 전용 서비스를 만들고 화면에 필요한 정보를 DTO로 반환했습니다. 6단계에서는 예약과 대기를 별도 엔티티로 관리하고, 내 목록에서 두 종류의 결과를 합쳤습니다.

대기 순번은 JPQL로 앞선 대기 수를 세는 방식으로 구현했습니다. 현재 구조에서 이해하기 쉬운 구현을 우선했으며, 대기 건수가 많아지면 목록과 순번을 한 번에 가져오는 쿼리로 개선할 수 있다고 생각합니다.

다음 부분을 중심으로 피드백 부탁드립니다.

- 예약·대기를 별도 엔티티로 관리하고 조회 서비스에서 합치는 책임 분리가 적절한지
- 기존 응답을 유지하며 예약 ID와 대기 ID를 분리한 DTO 구조가 적절한지
- 대기 순번 계산에서 쿼리 수를 줄이기 위한 개선 방향
- DB 제약 외에 동시 신청·취소의 일관성을 위해 필요한 트랜잭션과 잠금 범위
